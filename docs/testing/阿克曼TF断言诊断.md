# 阿克曼 TF 数量断言诊断与修复

2026-10-23，继续调查 [全部模型 ros2_control 验证](全部模型ros2_control验证.md) 中的 TF 数量断言失败。已通过恢复失败前置条件，复现并定位启动失败后的 RSP 子进程清理漏洞；修复后已从头完成整套功能回归及补充联调，全部已执行用例通过。本记录保留原始失败、修复前复现和修复后结果，不将单独复跑通过当作完整回归。

## 根因与复现

`SimulationHarness.close()` 原先只有在 `self.process.poll() is None` 时才向进程组发送 SIGINT。`poll()` 只判断 launch 主进程，不能说明它的子进程已经全部退出。

无人机案例启动时先安排 RSP，再导入仿真模型。当雷达参数包含插件不支持的 `point_layout` 时，SDF 导入抛出异常。Humble launch 在这条错误路径上退出码为 1，但已创建的 RSP 可以继续运行，甚至尚未来得及把 process-start 事件写入 launch 日志。旧清理逻辑看到主进程已经退出便跳过信号和等待，留下发布 `/tf_static` 的 RSP。新的 pytest 进程从相同的默认 domain 起点启动阿克曼，于是能发现两个 RSP。

本轮按原错误重建无人机组合 URDF，只注入 `point_layout: xyzirt_v1`，使用 domain 61。修复前的实测结果：

1. launch PID 81573 退出码为 1；清理后 RSP PID 81575 仍存活，PPID 为 1，PGID 仍为 81573。
2. 随后在同一 domain 启动阿克曼，机械模型、运动、里程计和 TF 数值检查通过，原数量断言再次失败。
3. `tf-graph.json` 明确记录 `/tf_static` 数量为 **2**，两个节点均为 `/robot_state_publisher`，DDS GID 不同；`/tf` 数量为 3，`/clock` 和 `/joint_states` 各为 1。

这解释了为什么新 domain 的单独复跑能够通过，也解释了为何只查 launch 自身日志或事后进程列表不足以定位问题。复现探针在采集证据后清理了自己创建的进程组。

## 原始证据与结论边界

原始日志没有保存断言时的计数和端点，不能补写为当时直接测得了数量 2。根因判断来自原始启动记录、进程组清理代码和恢复同一前置错误后的可重复失败：

| 时间 / 证据 | 观察 |
| --- | --- |
| 19:38:30，首次无人机错误日志 | SDF 导入报 `unknown parameter point_layout`，launch 退出码 1 |
| 19:38:31，同一目录独立 RSP 日志 | `robot_state_publisher_27861_1792755511134.log` 记录 RSP 在导入错误之后完成四个 link 的加载；launch 主日志没有对应 process-start 行 |
| Lima 的只读历史端口事件 | domain 61 的参与者端口 22662/22663 在 19:38:31 出现，19:51:41 才出现移除事件；端口事件本身不提供 PID，作为旁证使用 |
| 19:51:40，原阿克曼启动 | 新 RSP PID 33783，仿真 PID 33785，管理器 PID 33787；四轮车套件与多模型套件是先后执行 |
| 修复前故障注入 | 直接记录孤儿 RSP 的 PID/PPID/PGID，并在紧接的阿克曼用例中捕获数量 2 与两个 GID |

公共仿真 launch 和仿真节点没有新增 RSP 或静态 TF 发布者。修复针对测试工具对自己创建进程的清理职责，不更改使用者的 RSP 命名、命名空间或 remap，也不修改 DDS、QoS、系统网络或时钟设置。

## 修复与防回归

- [共享测试工具](../../litesim3d_test_support/litesim3d_test_support/harness.py) 始终向 `start_new_session=True` 创建的专属进程组发送 SIGINT，并等待整个组消失；即使主进程提前退出也必须清理其子进程。超时强杀仍使测试失败。`exit.json` 记录主进程是否先退出、是否强杀、组是否残留。
- [失败启动回归](../../scripts/integration/test_launch_cleanup.py) 使用真实无人机导入错误，先确认 RSP 已存在，再调用清理；断言进程组已经消失，然后立即在同一 domain 执行完整阿克曼模型/运动/TF 检查。不能通过换 domain 掩盖残留。
- [重复发布者负例](../../examples/ackermann/ackermann_sim/test/test_example.py) 在正常阿克曼中创建第二个真实 DDS writer，要求原断言仍然失败，并记录两个 GID。数量要求仍然是严格等于 1，没有自动重试。
- 每次启动保存 `launch-process.json`，判定时保存 `tf-graph.json`，SIGINT 前保存 `graph-before-shutdown.json`，包含节点名、命名空间、类型、GID、domain 和进程 ID。
- [完整回归入口](../../scripts/test_m3.sh) 补入此前漏掉的阿克曼/全向案例、控制硬件/配置、插件契约和公共 bringup；所有阶段串行执行，失败返回非零并保存 JUnit。

## 本轮完整回归发现的配套问题

第一次扩充后的完整回归在安装资源导入测试中有 4 项失败：旧测试直接读取 `runtime.yaml`，但案例已经改为由 launch 显式传入组合 Xacro，YAML 的 `robot.urdf` 按约定留空。已修正测试，使它与案例一样从已安装的 description/sim 包定位组合 Xacro，继续保留资源归属、模型、场景规模和 headless 运行断言。没有将路径写回参数文件。

该轮失败日志完整保留。首次修正测试时误将四轮车组合 Xacro 定位到 sim 包，针对性运行另有 2 项失败；随后按其真实 description 包路径修正，4 项导入测试通过。最终结果以此后重新开始的完整回归为准，不拼接这些针对性复跑。

## 完整回归中另外发现并修复的问题

根因修复后的第二轮完整运行（`run-20261023T124715Z`）没有再出现阿克曼双发布者，资源导入也全部通过，但还发现两项独立问题，因此这一轮仍判定为失败：

1. **硬件插件快速析构卡住。** `body_configuration` 卡在第一个 GPIO 测试，60 秒外层超时后 SIGINT 关闭 ROS，第一项才结束，后两项因 context 已关闭而失败。单核运行旧二进制也卡住，并在 4 秒后被探针强制终止。原因是析构的 `executor_.cancel()` 可以先于新线程进入 `spin()`；[Humble 的 spin 实现](https://github.com/ros2/rclcpp/blob/humble/rclcpp/src/rclcpp/executors/single_threaded_executor.cpp) 进入时重新设置运行标志，之前的取消不能保证随后线程退出。已在 [LiteSimSystem](../../litesim3d_ros2_control/src/system.cpp) 增加独立停止标志，改用最多等待 20 ms 的 `spin_once`，保证不依赖全局 `rclcpp::shutdown()` 就能回收线程。新增单核下连续 64 次初始化后立即析构的测试；修复后四项 body 配置测试在单核下共约 91 ms 通过，仍保留原 60 秒整组门槛。
2. **旧关节 TF 测试错误地以时钟到达推断 TF 历史就绪。** 原 `test_T_URD_19_articulated_tf[0.0]` 选取前 16 条 `/clock` 中的时刻后直接查询 TF。时钟和 TF 的发现、回调相互独立，所选时间可能早于 TF 缓存最早记录，之后继续等待也无法补回历史。延迟 TF 订阅的修复前探针明确复现请求 0.200000001 s、最早 TF 0.210000 s，返回 past extrapolation。原失败没有缓存快照，不能将探针时刻冒充原始时刻。已在 [原测试](../../litesim3d_ros2/test/test_ros.py) 先建立五个 link 的 TF 历史，再选择不早于该历史的时钟样本；保留原 0.5 秒查询等待及 1e-6 几何精度。三个角度分别覆盖普通和迟到 TF 订阅者，六项全部通过，并记录 `tf-readiness.json`。

第二轮的超时 wrapper 和探针创建的进程已按其所属进程组清理。第三轮从完整入口重新开始，包含以上修复，不以两个针对性检查替代整套回归。
