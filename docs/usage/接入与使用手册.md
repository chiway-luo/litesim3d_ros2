## 1. 能力范围与组成

这是一个 CPU 上运行的三维**运动学**仿真器。机器人按速度指令运动，三维几何负责碰撞和射线测距，ROS 2 桥接发布传感器、里程计、关节状态及仿真时钟。

| 可以直接使用 | 当前限制 |
| --- | --- |
| URDF、预展开 Xacro；箱体、球、圆柱、STL/OBJ/DAE 网格 | URDF 插件、Gazebo 扩展、ros2_control 配置不会自动执行 |
| 差速底盘、理想 Ackermann；连续坡面跟随、几何阻挡 | 无悬架、轮胎摩擦、接触力、自由落体、足式动力学或全向底盘 |
| 多线三维雷达、snapshot/rolling、测距误差和丢点 | 支持多线旋转、Mid-360 官方扫描表与 Mid-40 花瓣近似；不模拟真实光学与固件 |
| raw IMU、理想/带误差里程计 | IMU 不输出估计姿态；里程计噪声不会改变真实运动 |
| 1–4 个同构机器人共享世界、互相感知和碰撞 | 不能在一个 world 文件内分别配置不同 URDF/不同雷达 |
| 单机协调重置、状态诊断、运行清单、Ouster original 字段适配 | 多机完整会话重置、统一全局 RViz 场景尚未启用 |

本文介绍接口与接入方法；外部 SLAM/导航闭环需针对具体算法另行验证。平台、性能和稳定性测试范围集中记录在 [测试文档](../testing/README.md)。

| 包/目录 | 用途 |
| --- | --- |
| `litesim3d_core` | C++ 内核、模型/场景加载、传感器、独立 `sim_headless` |
| `litesim3d_ros2` | 单机/多机节点、launch、会话管理器、字段适配器、RViz 配置 |
| `litesim3d_interfaces` | `Step`、`SetPose`、`Reset` 服务和 `Contact` 消息 |
| `scripts` | 构建、Xacro 展开、测试和离线评测 |
| `docs/examples` | 本手册附带的配置与 Python 接入程序 |
| 外部 `artifacts/evidence/` | 运行清单和测试证据；不随源码仓库提交 |

## 2. 环境准备与第一次运行

### 2.1 首次构建

先按 [README](../../README.md) 安装依赖并 clone 仓库。下列命令及后续命令均从源码仓库根目录执行，基础 Humble 环境应已激活：

```bash
bash scripts/build.sh
source "$(python3 scripts/paths.py install)/setup.bash"
ros2 pkg prefix litesim3d_core
ros2 pkg executables litesim3d_ros2
```

应找到 `sim_node`、`sim_world_node`、`sim_session`、`sim_ouster_adapter` 和 `sim_cloud_probe`。构建目录、macOS 与标准 colcon 的区别见 [安装与构建](安装与构建.md)。标准 colcon 用户直接加载工作空间 `install/setup.bash`，不要调用没有前缀记录的 `scripts/paths.py install`。

### 2.2 每个终端都要准备环境

新终端先激活相同的 Humble 环境（Ubuntu Bash 使用 `source /opt/ros/humble/setup.bash`；macOS 激活自己的 RoboStack 环境），再进入 clone 的源码目录执行：

```bash
source "$(python3 scripts/paths.py install)/setup.bash"
export ROS_DOMAIN_ID=160 ROS_LOCALHOST_ONLY=1
evidence_dir="$(python3 scripts/paths.py evidence)"
mkdir -p "$evidence_dir"
export ROS_LOG_DIR="${evidence_dir}/manual-ros-logs"
mkdir -p "$ROS_LOG_DIR"
```

Zsh 使用 `setup.zsh`。所有通信终端使用相同 domain；每个 domain 同时只运行一个仿真世界。`ROS_LOCALHOST_ONLY=1` 限制为本机通信，日志写入外部产物目录，后续示例中的 `evidence_dir` 也由这里取得。

### 2.3 启动带雷达和 IMU 的单机示例

终端 A：

```bash
evidence_dir="$(python3 scripts/paths.py evidence)"
mkdir -p "$evidence_dir"
ros2 launch litesim3d_ros2 demo.launch.py \
  config:="$PWD/docs/examples/robot.yaml" \
  rviz:=true \
  manifest:="${evidence_dir}/manual-single.json"
```

需要纯后台运行时改为 `rviz:=false`。配置是 16 线 × 512 列、10 Hz rolling 雷达，200 Hz IMU，50 Hz odom，差速 R01 底盘；地面、前墙和立柱来自同一个 YAML。

终端 B（已完成 2.2）：

```bash
ros2 topic list
ros2 topic echo /sim/status --once
ros2 topic echo /points_raw --once --field header --qos-reliability best_effort
ros2 topic echo /imu/data_raw --once --qos-reliability best_effort
python3 docs/examples/ros_client.py --duration 5
```

示例程序输出 JSON。`connected: true` 表示收到了 clock、点云和 odom；本配置还应有非零 IMU 数量。它只验证通信，默认不发送控制指令。

终端 B 让机器人行驶 5 秒墙钟并在退出时发送零速度：

```bash
python3 docs/examples/ros_client.py --drive --linear 0.2 --angular 0.1 --duration 5
```

机器人应出现位姿变化，点云随运动改变。关闭时在终端 A 对完整 launch 按 Ctrl+C；必需的仿真或 RSP 子进程异常退出会使 launch 清理其余子进程并返回非零。

### 2.4 内置配置如何选择

内置配置目录为 `$(ros2 pkg prefix litesim3d_core)/share/litesim3d_core/config`。

| 文件 | 适合用途 |
| --- | --- |
| `demo.yaml` | M1 默认：32×1024 snapshot、平地、无 IMU |
| `m2.yaml` | 32×1024 rolling、IMU、地形跟随、4 个射线线程 |
| `ackermann.yaml` | 16×512 rolling、IMU、理想 Ackermann |
| `dynamic.yaml` | Ackermann + 移动箱体 |
| `m3_robot.yaml` | 供多机共享的 16×512 rolling 差速配置 |
| `m3_world.yaml` | 默认 4 机器人世界；用 `world.launch.py` 启动 |
| 本文 `examples/robot.yaml` | 带注释的单机教学配置，使用已安装 URDF 的 package URI |
| 本文 `examples/world.yaml` | 共享教学配置的两机器人世界 |

例如启动内置动态场景：

```bash
ros2 launch litesim3d_ros2 demo.launch.py \
  config:="$(ros2 pkg prefix litesim3d_core)/share/litesim3d_core/config/dynamic.yaml" \
  rviz:=true
```

## 3. 日常运行、控制、暂停和单步

### 3.1 Twist 控制与停车

默认只使用 `linear.x`（m/s）和 `angular.z`（rad/s）。正 x 向前，正 z 角速度为俯视逆时针。侧向、竖直、roll/pitch 角速度必须为 0。

```bash
ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.3}, angular: {z: 0.2}}'
```

按 Ctrl+C 停止发布。默认超过 **0.5 秒仿真时间**没有有效命令，机器人按配置减速度停车；不是墙钟 0.5 秒，也不是立即清零。可以显式发布零速度：

```bash
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.0}, angular: {z: 0.0}}'
```

超出最大速度的有效命令受限幅和加速度约束；NaN/Inf、错误 frame、非法分量、过期/未来时间戳被拒绝，**不会刷新有效命令超时**。同一物理步前多条有效命令可合并，实际应用记录见 manifest。

### 3.2 暂停和继续

```bash
ros2 service call /sim/pause std_srvs/srv/SetBool '{data: true}'
ros2 service call /sim/pause std_srvs/srv/SetBool '{data: false}'
```

暂停时仿真时间和传感器采样不推进；诊断仍可读取。暂停期间不一定有新的 `/clock` 消息，依赖消息的 `echo --once` 可能等待。此时通过 `/sim/status` 和服务响应判断状态。

要从暂停态启动：

```bash
ros2 launch litesim3d_ros2 demo.launch.py \
  config:="$PWD/docs/examples/robot.yaml" paused:=true rviz:=false
```

### 3.3 单步

先暂停，再执行：

```bash
ros2 service call /sim/step litesim3d_interfaces/srv/Step \
  '{request_id: "manual-step-001", steps: 20}'
```

默认步长 0.005 s，20 步推进 0.1 s 仿真时间。传感器按自身周期产生消息，所以单个 5 ms 步不一定发布雷达。rolling 点云还要等最后一个点采样完成。

| 规则 | 内容 |
| --- | --- |
| 状态 | 依赖就绪且处于 paused，运行态不能单步 |
| 步数 | 1–10000；还受约 512 MiB 单次点云输出预算限制，多机合计检查 |
| 请求 ID | 非空、最多 128 字节；一次新操作使用一个新 ID |
| 幂等 | 相同 ID + 相同步数重试返回原结果，不重复推进 |
| 冲突 | 同一 ID 换步数会拒绝 |
| 缓存 | 每次实验最多 4096 个成功的不同请求；满后开始新实验 |
| 返回 | `success`、`code`、`message`、`time_ns`；不能只看命令退出码 |

常见 Step code：0 成功；1 状态/就绪条件不满足；2 参数或输出预算非法；3 请求缓存满；4 同 ID 不同载荷。

### 3.4 初始位姿和运行中重置

常规初始位姿写在 YAML 的 `robot.initial_pose`，修改后重新启动。多机在 world 文件的每个 `robots[].xyz/rpy` 中设置。

`/sim/set_pose` 只允许实验尚未开始且内核仍为 `ready`；**`paused` 不等于 `ready`**。正常 launch 等待 RSP 后立即进入 running/paused，因此不应把这个服务当作日常瞬移按钮。它也不负责清空其他节点的 TF/算法历史。运行后回到起点使用第 14 节的协调 reset，或停止完整 launch 后重新启动。

### 3.5 无 ROS 的独立运行

```bash
evidence_dir="$(python3 scripts/paths.py evidence)"
mkdir -p "$evidence_dir"
lws_prefix="$(python3 scripts/paths.py install)"
mkdir -p "${evidence_dir}/manual"
"$lws_prefix/bin/sim_headless" "$PWD/docs/examples/robot.yaml" \
  400 "${evidence_dir}/manual/headless.json" 0.2 0.1 0
```

位置参数依次是：配置文件、步数、输出 JSON、可选 v、可选 ω、可选墙钟目标倍速。这里 400×0.005 = 2 秒仿真，每步持续输入 0.2 m/s 和 0.1 rad/s。步数范围 1–10000000；输出目录须先存在。正常结束退出码为 0，输出包含时间、点云槽位数量和运行清单。

`sim_headless` 不发布 ROS 话题，也不保存完整点云或 bag。它自己的最后一个 `rtf` 参数默认 0（无节拍限速）；此处节拍由该 CLI 参数决定，不能依赖 YAML 的 `real_time_factor`。需要 ROS 算法接入时使用 ROS 启动入口。

## 4. 启动入口和 ROS 参数

### 4.1 三类参数要放在正确位置

| 类型 | 设置位置 | 示例 |
| --- | --- | --- |
| 仿真模型参数 | 自定义 YAML | `simulation.step_size`、`robot.drive.max_v`、`lidars[].columns` |
| launch 参数 | `ros2 launch … 参数:=值` | `config:=…`、`rviz:=false` |
| 节点参数 | `ros2 run … --ros-args -p 参数:=值` 或自写 launch | `cmd_mode:=stamped`、`sensor_reliable:=true` |

**当前这些运行设置在启动时读取，没有实现动态重配置。** `ros2 param set` 即使修改了参数服务器的值，也不能据此认定传感器、模型或发布器已重新创建。修改 YAML、QoS、命令类型、TF 发布责任后，停止相关节点并重新启动。

### 4.2 单机 `demo.launch.py`

| launch 参数 | 默认 | 说明 |
| --- | --- | --- |
| `config` | 安装目录的 `config/demo.yaml` | 单机 YAML 文件路径，推荐绝对路径 |
| `namespace` | 空 | ROS 命名空间，如 `robot` |
| `frame_prefix` | 空 | TF/frame 前缀，如 `robot/`，无前导 `/`，有结尾 `/` |
| `paused` | `false` | 就绪后保持暂停 |
| `rviz` | `true` | 启动随附 RViz |
| `manifest` | 空 | 非空时写运行 JSON，父目录先创建 |

查看实际安装版本：

```bash
ros2 launch litesim3d_ros2 demo.launch.py --show-args
```

此 launch **未暴露** `cmd_mode`、`sensor_reliable`、`publish_odom_tf` 等节点参数。需要这些设置时用下一节的独立节点方式，或在自己的 ROS launch 中向 Node 的 `parameters` 传入。不要把未声明的参数写在 demo launch 后并假定它生效。

### 4.3 单机高级设置：分别启动 RSP 和仿真节点

先停止此前的 demo launch。终端 A：

```bash
evidence_dir="$(python3 scripts/paths.py evidence)"
mkdir -p "$evidence_dir"
python3 docs/examples/make_rsp_params.py \
  docs/examples/robot.yaml "${evidence_dir}/manual-rsp.yaml"
ros2 run robot_state_publisher robot_state_publisher \
  --ros-args --params-file "${evidence_dir}/manual-rsp.yaml"
```

终端 B（已完成 2.2）：

```bash
evidence_dir="$(python3 scripts/paths.py evidence)"
mkdir -p "$evidence_dir"
ros2 run litesim3d_ros2 sim_node --ros-args \
  -p config:="$PWD/docs/examples/robot.yaml" \
  -p use_sim_time:=true \
  -p cmd_mode:=stamped \
  -p sensor_reliable:=true \
  -p manifest_path:="${evidence_dir}/manual-advanced.json"
```

终端 C：

```bash
python3 docs/examples/ros_client.py --stamped --drive --linear 0.2 --duration 5
```

这次 `/cmd_vel` 类型为 TwistStamped。切回默认 Twist 时重新启动 sim_node 并省略 `cmd_mode` 或设置 `twist`，消费端也同步切换。独立启动的两个进程需分别 Ctrl+C。

带命名空间时，RSP 和 sim_node 都用 `--ros-args -r __ns:=/robot`，生成 RSP 参数时另加 `--frame-prefix robot/`，sim_node 另加 `-p frame_prefix:=robot/`。不要只给话题加 namespace 却保留全局 frame 名。

### 4.4 单机节点参数表

| `sim_node` 参数 | 默认 | 说明 |
| --- | --- | --- |
| `config` | 空，必须提供 | 单机 YAML 文件路径 |
| `use_sim_time` | ROS 通用参数；launch 设为 true | 算法、RSP、RViz 也应启用 |
| `frame_prefix` | 空 | 同时影响消息 frame 和桥接发布的 TF |
| `cmd_mode` | `twist` | `twist` / `stamped`；一个话题只选一种 |
| `sensor_reliable` | false | false 为 best effort，true 为 reliable；点云/IMU KEEP_LAST 5 |
| `publish_odom_tf` | true | 是否发布 `odom → URDF root` |
| `external_odom_tf` | false | 外部发布责任声明；与 `publish_odom_tf: true` 同时启用会拒绝 |
| `wait_for_robot_state_publisher` | true | 等待同命名空间、指定名称的 RSP 订阅 joint_states |
| `robot_state_publisher_name` | `robot_state_publisher` | RSP 节点名，不是包名或 TF frame |
| `startup_timeout` | 10.0 | 正数，等待依赖的墙钟秒数 |
| `start_paused` | false | 依赖就绪后是否暂停 |
| `manifest_path` | 空 | 运行清单输出路径 |
| `initial_pose_override` | 空数组 | 可选 7 个 double：`[x,y,z,qx,qy,qz,qw]`，主要用于会话重置 |
| `test_drop_frames` | 0 | 测试故障注入，0–100；正常使用保持 0 |

若外部估计器发布 odom TF，独立 sim_node 加 `-p publish_odom_tf:=false -p external_odom_tf:=true`。关闭等待 RSP 不会自动补齐内部 link TF，常规使用保留等待。

### 4.5 多机 `world.launch.py`

| launch 参数 | 默认 | 说明 |
| --- | --- | --- |
| `config` | 安装目录的 `config/m3_world.yaml` | 世界配置路径 |
| `paused` | false | 整个世界暂停启动 |
| `manifest` | 空 | 整个世界运行清单 |
| `cmd_mode` | twist | 所有机器人的命令类型统一选择 |
| `sensor_reliable` | false | 所有机器人的点云/IMU可靠性统一选择 |
| `publish_odom_tf` | true | false 时全部机器人的 odom TF 交给外部估计器 |
| `external_odom_tf_robots` | 空 | 逗号分隔 ID，如 `r1,r3`；仅关闭这些机器人的 odom TF |
| `startup_timeout` | 15.0 | 正数，等待各 RSP 的墙钟上限 |

world launch 没有 `rviz`、`namespace` 或 `frame_prefix` 参数。每个 ID 自动成为 namespace 和 frame 前缀。布尔设置写 `true`/`false`。

直接使用 `sim_world_node` 时，节点参数为 `config`、`use_sim_time`、`start_paused`、`manifest_path`、`cmd_mode`、`sensor_reliable`、`publish_odom_tf`、`external_odom_tf_robots`、`wait_for_robot_state_publisher`、`robot_state_publisher_name`、`startup_timeout`。默认值与上表/单机等待设置一致，startup_timeout 为 15.0；其中 `external_odom_tf_robots` 是字符串数组，launch 的逗号文本会转换为数组。没有单机的 `initial_pose_override`、`external_odom_tf`、`test_drop_frames` 参数。使用 world launch 可自动管理各机器人的 RSP。

## 5. 接入自己的 URDF、Xacro 与网格

### 5.1 推荐目录与迁移步骤

需要一个可以直接修改的完整四轮车工程时，先看 [wheel_car_4w 示例](../../examples/wheel_car_4w/README.md)。它已在 `examples/wheel_car_4w` 下拆分模型包和仿真包，包含完整中文注释参数，一条 `ros2 launch wheel_car_4w_sim wheel_car_4w.launch.py` 即可启动。

把自己的资源放入独立目录，保留内置样例。例如：

```text
my_sim/
├── config/robot.yaml
├── config/world.yaml
├── urdf/my_robot.urdf
└── meshes/body.stl
```

1. 复制本文 `examples/robot.yaml`，将 `robot.urdf` 改为 `../urdf/my_robot.urdf`。
2. 核对 base_link、左右轮关节、轮径/轮距、雷达/IMU link 和安装位置。
3. 先用 `sim_headless` 跑 1 步做模型/初始碰撞预检，再运行 400 步验证传感器采样。
4. 用 `demo.launch.py config:=绝对路径` 启动，检查 TF、点云、odom 后再接控制程序。

如果复制内置配置，注意原文件里的 `../urdf/…`：**只复制 YAML 会改变相对路径基准**。可以一并复制 config/urdf/meshes，或把 URDF 改成绝对路径、`package://包名/urdf/文件.urdf`。

| 路径写法 | 解析基准 |
| --- | --- |
| YAML 的 `robot.urdf`、场景 mesh `uri` | 该 YAML 所在目录 |
| URDF 的 mesh `filename` | 该 URDF 所在目录 |
| world 的 `config` | world YAML 所在目录 |
| `package://my_description/meshes/body.stl` | 已 source 的 ament 安装前缀中该包的 share 目录 |
| `/绝对路径/文件`、`file:///绝对路径/文件` | 对应本地文件 |

这些路径不是相对于启动终端。`config:=` 本身使用普通文件路径；package URI 用在配置中的资源引用。相对路径模型若要让 RViz 也正确加载，优先安装为 ROS description 包并使用 package URI，或在 URDF 中使用绝对 mesh 路径。

### 5.2 URDF 的实际要求

| 项目 | 要求 |
| --- | --- |
| 坐标 | 右手系，x 前、y 左、z 上；长度米、角度弧度 |
| 模型 | URDF 1.0，恰好一个 root，无环、无重复 link/joint，所有引用存在 |
| 几何 | box、sphere、cylinder、STL/OBJ/DAE；支持 origin 和正数 mesh scale |
| 关节 | fixed、revolute、continuous、prismatic；支持无环 mimic |
| 基座 | YAML 指定的 `base_link` 存在，且到 URDF root 的链全部为 fixed |
| visual/collision | 有 visual 的实体默认必须有 collision；纯坐标 link 可以没有几何 |
| 非驱动关节 | 保持 `initial_joints` 指定的初值；没有通用关节位置/力矩命令接口 |
| 惯性 | 提供时读取并检查质量等信息；不据此计算动力学 |
| 规模 | 最多 4096 links、4095 joints，关节链深度受 128 层预算约束 |

`<gazebo>`、`<transmission>` 等扩展标签会列入导入报告的 `ignored_extensions`；它们不会自动生成传感器、驱动插件或控制器。雷达、IMU 必须在仿真 YAML 中声明，并绑定已有 link。

### 5.3 驱动轮约束：模型接入最常见失败点

当前底盘适配有明确几何约束，任意轮式 URDF 不能保证直接加载：

| 项目 | 当前要求 |
| --- | --- |
| 左右关节 | 两个不同的 continuous 关节，不是 mimic，从 YAML 指定名称读取 |
| 轮轴 | 在 base 坐标系中指向 **+y**；左右轮都采用该方向 |
| 轮子 collision | 居中、与关节共轴的圆柱，半径与 `wheel_radius` 相差小于 1e-6 m |
| 轮距 | 两轮 link 原点距离与 `wheel_separation` 相差小于 1e-6 m，左轮 y 大于右轮 y |
| 关节树 | 两个驱动轮 link 必须是叶节点，不能再挂子 link |
| 速度 limit | 至少覆盖 `(max_v + max_w × wheel_separation / 2) / wheel_radius` rad/s |
| 支撑 link | `support_links` 中的名称必须存在，只列实际作为轮面支撑的 link |

随附 [r01.urdf](../../litesim3d_core/resources/urdf/r01.urdf) 是可工作模板：两轮原点为 `(0,±0.25,0.1)`，半径 0.1 m，轮距 0.5 m，关节 axis 为 `0 1 0`；圆柱的本地轴为 z，因此轮子 collision 用绕 x 的旋转使其轴与 y 对齐。

R01 的 base 原点在地面参考平面，车体 box 中心 z=0.3；`initial_pose.xyz.z=0` 不是把车体中心放在地面。换模型时应统一 base 原点、轮子高度和地形 clearance，避免起始穿透。

模型只缺 collision、且你确认可用 visual 替代时，可以显式设置：

```yaml
robot:
  # 保留 urdf、drive 等其他字段
  visual_collision_fallback: true
  sensor_geometry: visual
  sensor_overrides:
    base_link: collision
```

这是对原有 `robot` 映射的修改，不是再添加第二个 `robot`。fallback 会写入报告，复杂 visual 网格可能提高碰撞成本。`sensor_geometry` 和每个 override 只支持 `visual` 或 `collision`；没有 visual 但有 collision 的模型需显式选择 collision。

### 5.4 Xacro 先展开

在已进入 Humble 的终端中：

```bash
evidence_dir="$(python3 scripts/paths.py evidence)"
mkdir -p "$evidence_dir"
python3 scripts/prepare_xacro.py \
  litesim3d_core/resources/urdf/r04.xacro \
  "${evidence_dir}/manual/r04.urdf"
```

自己的模型可追加 Xacro 映射参数，例如 `wheel_radius:=0.1`；参数名以模型定义为准。相对 mesh 路径默认按输入 Xacro 所在目录解析，必要时用 `--resource-base /模型资源目录` 指定。

工具同时生成 `输出.urdf.json`，记录源文件、包含文件、映射及资源哈希，并将相对 mesh 路径改成绝对路径。随后把 YAML `robot.urdf` 指向生成的 `.urdf`。不要直接把 `.xacro` 作为已经展开的 URDF 传给仿真。

### 5.5 网格与自碰撞可见性

网格坐标默认按米处理；毫米模型通常需要 `scale: [0.001, 0.001, 0.001]`。网格碰撞是三角形表面，不等价于实体动力学或完整体积占据；不要用机器人起点藏在大型闭合 mesh 内部的方式验证自由空间。

雷达默认过滤自身传感器 link，仍可看到其他车体部分。若只关心环境，设 `self_filter: robot`；需要保留部分自体回波时设 `self_filter: links` 并填写 `excluded_links`。详见第 8 节。

## 6. 场景、地形与动态障碍

### 6.1 实体配置

`entities` 是单机配置根节点下的列表；必须存在，可以是空列表，最多 10000 个实体。ID 非空且唯一。下面是追加到列表中的一个实体：

```yaml
- id: obstacle_box
  pose: {xyz: [2.0, 1.0, 0.5], rpy: [0.0, 0.0, 0.3]}
  geometry: {type: box, size: [0.6, 0.6, 1.0]}
  reflectivity: 0.7
  support: false
```

| 字段 | 默认/要求 |
| --- | --- |
| `id` | 必填、唯一 |
| `pose.xyz` / `pose.rpy` | 缺省 `[0,0,0]`；世界坐标，分别为米和弧度 |
| `reflectivity` | 0.5，范围 [0,1]，作为合成激光强度 |
| `support` | false；true 表示候选支撑面，不表示所有碰撞都忽略 |
| `geometry` | 一个形状同时用于显示、碰撞和雷达 |
| `visual`、`collision`、`sensor_geometry` | 使用独立角色时三者都必须提供，不能再混用 `geometry` |
| `motion` | 缺省静态；提供时按下节运动 |

支持的 geometry：

```yaml
{type: box, size: [1.0, 2.0, 0.5]}
{type: sphere, radius: 0.3}
{type: cylinder, radius: 0.3, length: 2.0}
{type: mesh, uri: ../meshes/room.obj, scale: [1.0, 1.0, 1.0]}
```

以上四行是四种**替代写法**，分别作为某个 geometry 的值，不要原样拼成一份根配置。尺寸、半径、长度、scale 必须是正数；圆柱轴沿实体局部 z。实体 pose 再把形状变换到世界坐标。

显示高精度网格、碰撞低成本包围盒的例子：

```yaml
- id: machine
  pose: {xyz: [4, 3, 1]}
  visual: {type: mesh, uri: ../meshes/machine.stl, scale: [1, 1, 1]}
  collision: {type: box, size: [2, 1, 2]}
  sensor_geometry: {type: mesh, uri: ../meshes/machine.stl, scale: [1, 1, 1]}
```

这个片段要求你提供真实存在的 `machine.stl`。简化 collision 会改变通行空间，应以实际需要选取。

### 6.2 平地与连续坡面

平地示例：box 大小 `[30,30,0.2]`，中心 `[0,0,-0.1]`，上表面 z=0，`support: true`。未启用 terrain 时，支撑必须是未旋转且上表面 z=0 的轴对齐 box。

启用连续坡面，在根配置中设置：

```yaml
terrain:
  enabled: true
  max_slope_deg: 20.0
  clearance_m: 0.0
  continuity_m: 0.02
```

| 参数 | 默认与范围 | 实际作用 |
| --- | --- | --- |
| `enabled` | 整个 terrain 缺省时 false | 若写了 terrain 映射但省略 enabled，解析器默认 **true**；建议总是显式填写 |
| `max_slope_deg` | 20，严格在 (0,90) 内 | 可通行支撑坡度上限，过陡会停住 |
| `clearance_m` | 0，≥0 | base 参考点相对支撑面的高度偏移，不是车体最低点间隙 |
| `continuity_m` | 0.02，(0,0.1] m | 连续层高度关联范围，不是允许攀爬的台阶高度 |

支撑来自 `support: true` 实体的 **collision**：箱体局部上表面，或朝上的 mesh 三角面。多层场景按前一支撑高度关联；桥底、立面等其他碰撞仍存在。网格三角形法向需朝上。

机器人支撑采样由 URDF 中 `drive.support_links` 对应的 collision 几何确定：圆柱轮检查轮宽中心及两侧边缘，所有声明轮子都必须有支撑。该列表不能遗漏前轮或 mimic 轮，也不能包含没有 collision 的 link；更改轮距后采样位置随模型变化。球形和其他形状的采样规则见 [M2 使用说明](M2使用说明.md)。

测试单一斜面时，可以将原地面替换为下列 5° 倾斜 box，并开启 terrain。示例起点保留 `[0,0,0]`，不要同时保留原水平地面覆盖斜面：

```yaml
- id: slope_ground
  pose: {xyz: [0, 0, -0.1], rpy: [0, -0.0872664626, 0]}
  geometry: {type: box, size: [30, 30, 0.2]}
  support: true
```

实际道路使用连续坡面或平滑网格。机器人会跟随支撑高度和法向调整 z/roll/pitch；遇到空洞、台阶、坡度或连续性超限会停止，不会自由落体或自动爬阶。拼接处的不光滑加速度不能当作真实车辆悬架响应。

### 6.3 动态实体

```yaml
- id: moving_box
  pose: {xyz: [3, -3, 0.5]}
  geometry: {type: box, size: [0.3, 0.3, 1.0]}
  motion:
    linear_velocity: [0, 0.15, 0]
    yaw_rate: 0.2
```

速度是**世界坐标系**的恒定线速度（m/s）和绕世界 z 的角速度（rad/s），时间原点为本次仿真开始。线速度默认零、yaw_rate 默认 0；线速度范数≤100、角速度绝对值≤100。最多 128 个动态实体；`motion` 不能与 `support: true` 同用。

rolling 雷达按每点时间查询动态物体。碰撞按保守相对扫掠包络处理，机器人与移动障碍可能提前停止；冻结时刻写入 manifest。没有弹性碰撞、推动物体、反弹或自动绕行。当前 ROS 接口没有在线增删障碍/更换场景服务，修改配置后重启。

## 7. 仿真和底盘参数完整参考

本节及第 8–9 节列的是**解析器缺省值**，内置示例可能显式覆盖。根配置必须声明 `schema_version: 1`、`units: m_rad_s`、`robot`、非空 `lidars` 列表和 `entities` 列表。已定义结构中的未知字段会拒绝，不能随意添加自定义键；向量使用三个有限数值。

### 7.1 `simulation`

| 字段 | 默认 | 单位/范围/说明 |
| --- | --- | --- |
| `step_size` | 0.005 | 秒，[1e-9,0.1]；转换成整数纳秒，决定运动积分步长 |
| `seed` | 42 | uint64 随机种子；影响测量噪声和 dropout |
| `odom_rate` | 50 | Hz，(0,1000]，按仿真时间 |
| `command_timeout` | 0.5 | 正数，仿真秒；有效速度命令看门狗 |
| `real_time_factor` | 1.0 | [0,100]；1 为目标实时，0 为尽快运行；ROS 节点的墙钟节拍 |
| `threads` | 1 | 整数 1–4，射线工作线程预算 |
| `history_limit` | 8192 | 轨迹状态数，[4,65536]；rolling/多机按采样事件率预检所需历史 |
| `journal_limit` | 4096 | 最近命令/接触日志容量，[1,65536]；截断量另行计数 |

传感器频率是仿真频率。例如 RTF=0.5 时，10 Hz 雷达在墙钟每秒约有 5 帧；硬件过载时实际 RTF 还会下降。降低步长会提高运动积分开销，也会增加 rolling 历史需求。

### 7.2 `robot`

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `id` | `robot_0` | 单机真值/诊断标识；**不会自动创建 ROS namespace** |
| `urdf` | 必填 | URDF 路径或资源 URI |
| `base_link` | `base_link` | 运动参考 link，须存在并与 root 固连 |
| `motion_model` | `differential_drive` | 另支持 `ackermann` |
| `initial_pose.xyz` | `[0,0,0]` | 世界初始位置，米 |
| `initial_pose.rpy` | `[0,0,0]` | 世界初始姿态，弧度；关闭地形时必须水平 |
| `initial_joints` | `{}` | 关节名→初值，转动为弧度、移动为米；满足关节限位/mimic 约束 |
| `visual_collision_fallback` | false | 显式允许缺 collision 时用 visual 替代 |
| `sensor_geometry` | visual | 机器人被射线查询的几何：visual/collision |
| `sensor_overrides` | `{}` | link 名→visual/collision；按 link 覆盖 |
| `drive` | 见下表 | 与 URDF 驱动几何一致 |

### 7.3 `robot.drive`

| 字段 | 默认 | 单位/约束 |
| --- | --- | --- |
| `wheel_radius` | 0.1 | m，>0，与两驱动轮半径一致 |
| `wheel_separation` | 0.5 | m，>0，与两轮原点距离一致 |
| `left_joint` / `right_joint` | left_wheel_joint / right_wheel_joint | 不同且存在的连续驱动关节 |
| `support_links` | `[left_wheel,right_wheel]` | 可作为支撑接触处理的 link 集合 |
| `max_v` | 1.0 | m/s，>0，线速度绝对值上限 |
| `max_w` | 2.0 | rad/s，>0，角速度绝对值上限 |
| `acceleration` | 0.5 | m/s²，>0 |
| `deceleration` | 1.0 | m/s²，>0 |
| `angular_acceleration` | 2.0 | rad/s²，>0 |
| `unlimited_acceleration` | false | true 时跳过加速度限幅；各加速度字段仍须为正 |
| `wheelbase` | 1.0 | m，>0；Ackermann 轴距，差速模式下也检查合法性 |
| `max_steering_rad` | 0.6 | 弧度，严格在 (0,π/2) 内；Ackermann 最大转角 |

差速轮速按 `ω左=(v−ω×wheel_separation/2)/wheel_radius`、`ω右=(v+ω×wheel_separation/2)/wheel_radius` 计算。配置的半径和轮距同时影响运动与关节状态，应与模型匹配。

Ackermann 修改 `robot.motion_model: ackermann`，并设置 drive 下的 wheelbase/max_steering_rad。输入仍是 v/ω，满足：

```text
|ω| ≤ |v| × tan(max_steering_rad) / wheelbase
```

允许倒车；v=0 时不能原地转向。这里采用理想后轴参考点自行车模型，随附 R01 是等效后轴示例，不会自动建立真实前轮转向关节或悬架。

## 8. 激光雷达参数与点云语义

2026-10-18增加了机械多线、球面带和圆锥花瓣扫描，以及VLP-16、Mid-360、Mid-40预设。Mid-360已改为Livox官方逐点角度表，按20万方向/秒和原始顺序发射，4秒序列循环。型号切换、视场/距离设置和近似范围见 [四轮车雷达配置说明](../../examples/wheel_car_4w/雷达配置说明.md)。`scan_pattern` 决定空间轨迹，`scan_mode` 决定帧内时间采样；两者独立。

### 8.1 `lidars[]` 参数

每个配置必须有 1–16 个雷达。所有雷达和 IMU 的 name、topic 必须彼此唯一。多机时 topic 必须是相对名称，如 `points_raw`。

| 字段 | 默认 | 单位/约束 |
| --- | --- | --- |
| `name` | 必填 | 传感器标识，也参与确定性随机流 |
| `link` | 必填 | URDF 中实际存在的传感器 link，安装外参由 URDF 决定 |
| `topic` | points_raw | PointCloud2 输出话题 |
| `rate_hz` | 10 | Hz，(0,1000]，扫描帧率 |
| `columns` | 1024 | spinning为每线水平列数，其他模式为每帧点槽数；整数 1–65536 |
| `vertical_angles_deg` | spinning必填 | 按 ring 顺序给出角度，范围 [-90,90]°；其他模式只能省略或填 `[0]` |
| `rings` | 角度数组长度 | spinning与数组长度一致；非重复模式固定1，ring字段为兼容占位 |
| `min_range_m` | 0.1 | m，≥0 |
| `max_range_m` | 100 | m，严格大于最小量程 |
| `publish_range_boundary` | false | 开启后额外发布`<topic>/range_boundary`，用于显示无命中射线的最大量程终点；本例默认开启 |
| `horizontal_start_deg` | -180 | 水平起点角度 |
| `horizontal_end_deg` | 180 | 严格大于起点，总跨度≤360°；采样区间左闭右开 |
| `scan_mode` | snapshot | snapshot / rolling |
| `scan_pattern` | spinning | spinning / spherical / rosette / livox_mid360；旧配置行为保持兼容 |
| `pattern_file` | 无 | 仅livox_mid360必填；package URI、绝对路径或相对配置路径 |
| `vertical_min_deg/max_deg` | spherical: -90 / 90；livox_mid360: -7 / 52 | −90≤下界<上界≤90；前者生成轨迹，后者只裁剪原始方向 |
| `cone_half_angle_deg` | 19.2 | 仅rosette，(0,90]，圆锥全张角为2倍 |
| `pattern_hz` | 100 | 仅spherical/rosette，(0,10000]；点率≥4×√2×基频；仿真假设，不是厂家镜片转速 |
| `point_layout` | xyzirt_v1 | 当前原始输出只支持这一布局 |
| `self_filter` | sensor_link | sensor_link / robot / links |
| `excluded_links` | `[]` | 额外排除的自身 link，必须存在 |
| `ring_delays_s` | `[]`，等价各线 0 | spinning非空时与rings等长；每项≥0且小于一个列周期；其他模式必须为空 |
| `range_bias_m` | 0 | m，有限的固定偏置，可正可负 |
| `range_sigma_m` | 0 | m，≥0，每点独立高斯标准差 |
| `dropout` | 0 | [0,1]，有效回波丢点概率 |

单雷达以及所有雷达合计点槽位不得超过4194304。每个雷达按`rings × columns`计数，开启`publish_range_boundary`时按两份计入；单步输出内存预算也包含辅助点云。实际负载约随点数×帧率×机器人数量增长。

`livox_mid360` 必须满足 `columns × rate_hz = 200000`，默认10 Hz/20000槽；20 Hz改为10000槽。官方表位于 `package://litesim3d_core/lidar_patterns/mid360.csv`，包含80万方向，4秒后循环；更改封帧频率不改变方向顺序。水平/垂直边界仅屏蔽原有方向，裁掉的槽位保留NaN与逐点时间。文件最大64 MiB、最多200万行，解析结果共享且只读；manifest记录实际哈希、行数及循环周期。[来源、MIT许可与建模限制](../../litesim3d_core/resources/lidar_patterns/README.md)

`sensor_link` 排除当前传感器 link；`robot` 排除整个自身机器人；`links` 只按 excluded_links 排除。多机下这不会让其他机器人消失，其他机器人按 collision 几何参与感知。

例如第二个雷达需要 URDF 中已有 `rear_lidar_link`，然后在 lidars 列表中追加独立 name、link、topic 和角度数组。仅改 YAML link 名不会创建安装坐标系。

### 8.2 时间与滚动畸变

`header.stamp` 是扫描开始的仿真时刻。snapshot 所有点 `time=0`；rolling 第 r 线、第 c 列的相对时间为：

```text
time(r,c) = c / (rate_hz × columns) + ring_delays_s[r]
```

内部采样时间四舍五入到整数纳秒，原始 `time` 字段用 float32 秒。ring 延迟必须落在一个列周期内，最后一个采样必须在本扫描周期结束前；snapshot 不允许非零 ring 延迟。

rolling 坐标在**该点采样时刻的雷达局部坐标系**中，整帧只在最后一个点采完后发布。这就是运动畸变来源；消费者不能把它当作已经对齐到扫描起点的去畸变云。需要去畸变时，用每点时间及 IMU/估计运动插值完成，时间单位转换要与目标算法一致。

### 8.3 原始 `xyzirt_v1` 布局

PointCloud2 为小端，`height=rings`，`width=columns`，`point_step=24`，`row_step=columns×24`。按 ring 行、column 列组织；ring 是角度数组的零基索引，不保证按仰角大小排序。

非重复模式height=1，ring恒为0，不能当成真实机械线号；仍输出相同24字节标准PointCloud2，不模拟厂家专用消息或UDP。rosette用圆锥半角定义视场，不能混用水平/垂直矩形边界；spherical的两个角范围形成球面带，不表示固定空间中的点云球壳。

| 字段 | 字节偏移 | 类型 | 单位 |
| --- | --- | --- | --- |
| x/y/z | 0/4/8 | float32 | m，传感器局部坐标 |
| intensity | 12 | float32 | 合成归一化反射率 [0,1] |
| ring | 16 | uint16 | 线号，从 0 开始 |
| 保留字节 | 18–19 | 两个零字节，无 PointField | 不作数据解释 |
| time | 20 | float32 | 相对 header 的秒 |

无回波、丢点、噪声后越界点保留槽位，xyz 写 NaN、intensity 为 0，ring/time 仍保留；存在无效点时 `is_dense=false`。算法先过滤非有限 xyz；不能把 NaN 当作原点或把所有强度为 0 的点都认为无效，因为实体可设反射率 0。

可选的`<topic>/range_boundary`使用相同布局、帧时间、ring/time和QoS：在最大量程内没有几何命中的方向，xyz为`单位方向×max_range_m`；其他槽位为NaN，intensity为0。它是最大范围可视化，不是回波，也不用于建图。视场裁剪、盲区遮挡、随机丢点和噪声后越界不生成最远点；辅助topic与其他雷达/IMU topic不能重名。四轮示例用淡蓝色单独显示，详见雷达配置说明。

当前 intensity 是命中实体的固定 reflectivity，不含真实光功率、入射角衰减或材料标定。随机种子和相同输入可复现噪声；改变线程数不会靠共享随机引擎重新打乱点槽位。

## 9. IMU 和里程计配置

### 9.1 `imus[]`

不写 imus 表示没有 IMU；最多 16 个。向根配置加入：

```yaml
imus:
  - name: imu
    link: base_link
    topic: imu/data_raw
    rate_hz: 200
    accel_bias: [0.01, 0.0, 0.0]
    gyro_bias: [0.0, 0.0, 0.001]
    accel_sigma: [0.02, 0.02, 0.02]
    gyro_sigma: [0.001, 0.001, 0.001]
```

| 字段 | 缺省 | 单位/说明 |
| --- | --- | --- |
| name / link / topic | imu / base_link / imu/data_raw | 多个 IMU 必须显式区分名称和话题 |
| rate_hz | 200 | (0,2000] Hz |
| accel_bias | `[0,0,0]` | m/s²，传感器三轴固定偏置 |
| gyro_bias | `[0,0,0]` | rad/s，传感器三轴固定偏置 |
| accel_sigma | `[0,0,0]` | m/s²，非负的每样本标准差 |
| gyro_sigma | `[0,0,0]` | rad/s，非负的每样本标准差 |

sigma 是每样本噪声标准差，不是噪声密度；当前没有 bias random walk 参数。输出考虑世界重力、安装旋转、角加速度和偏心向心项。零噪声、水平静止、安装轴一致时，线加速度应约为 `[0,0,9.80665]`，角速度约为零。

raw IMU 不提供姿态估计，`orientation_covariance[0]=-1`；不要把消息中的占位单位四元数当作测得姿态。已知噪声方差填入加速度/角速度协方差对角线；全零协方差表示未声明不确定性，不应直接解释为真实无误差传感器。

### 9.2 `odom`

```yaml
odom:
  mode: noisy
  linear_scale: 1.01
  angular_scale: 1.0
  linear_bias: 0.0
  angular_bias: 0.001
  linear_sigma: 0.005
  angular_sigma: 0.002
```

| 字段 | 默认 | 单位/说明 |
| --- | --- | --- |
| mode | ideal | ideal / noisy |
| linear_scale / angular_scale | 1 / 1 | 正数，无量纲 |
| linear_bias / angular_bias | 0 / 0 | m/s、rad/s 的速度偏置 |
| linear_sigma / angular_sigma | 0 / 0 | 非负的速度噪声标准差，m/s、rad/s |
| pose_covariance | 36 个 0 | 6×6 行主序，顺序 x,y,z,roll,pitch,yaw |
| twist_covariance | 36 个 0 | 同上，顺序 vx,vy,vz,wx,wy,wz |

`ideal` 模式不能配置非默认误差；要开启误差须同时改为 noisy。误差在里程计通道积分，世界真值、碰撞、激光和 IMU 的真实运动不随之改变。里程计协方差由用户显式声明，不会根据 sigma 自动传播成位置协方差。

两种协方差如提供，都必须有 36 个有限值，矩阵对称且半正定。可用下面代码构造仅对角线非零的 YAML 列表，再放入 `odom.pose_covariance` 或 `twist_covariance`：

```python
diagonal = [0.01, 0.01, 0.01, 0.001, 0.001, 0.001]  # 方差，按实际模型选择
covariance = [diagonal[row] if row == col else 0.0
              for row in range(6) for col in range(6)]
```

odom 的 pose 在局部 odom 坐标系中，twist 在机器人 base_link 中。world 初始位置与 odom 原点不相同，不能直接将二者坐标数值逐项比较；离线评测需先明确固定初始对齐。

## 10. ROS 2 接口、时间、TF 与 QoS

### 10.1 单机话题表

下表使用根命名空间和本文示例。传感器话题可以由 YAML 改名。

| 话题 | 类型 | 方向/频率 | 发布 QoS |
| --- | --- | --- | --- |
| `/cmd_vel` | geometry_msgs/msg/Twist 或 TwistStamped | 控制器→仿真；建议持续 10 Hz 以上，按超时配置调整 | 仿真订阅 reliable、depth 1 |
| `/points_raw` | sensor_msgs/msg/PointCloud2 | 仿真→消费端；雷达 rate_hz | best effort、depth 5，可切换 reliable |
| `/imu/data_raw` | sensor_msgs/msg/Imu | 配置 IMU 后发布，rate_hz | 同点云 |
| `/odom` | nav_msgs/msg/Odometry | 仿真→估计器/控制器；odom_rate | reliable、depth 10 |
| `/joint_states` | sensor_msgs/msg/JointState | 仿真→RSP；随仿真状态更新 | reliable、depth 10 |
| `/robot_description` | std_msgs/msg/String | URDF 描述 | reliable、transient local、depth 1 |
| `/clock` | rosgraph_msgs/msg/Clock | 唯一仿真时钟 | best effort、depth 1 |
| `/tf`、`/tf_static` | tf2_msgs/msg/TFMessage | 桥接和 RSP 按职责发布 | 使用 TF/RSP 的 QoS，消费者用标准 TF API |
| `/scene` | visualization_msgs/msg/MarkerArray | 单机环境显示，动态物体刷新 | reliable、transient local、depth 1 |
| `/trajectory` | nav_msgs/msg/Path | 单机轨迹显示 | reliable、depth 1 |
| `/sim/status` | diagnostic_msgs/msg/DiagnosticArray | 诊断，按墙钟周期更新，暂停仍可读 | reliable、depth 10 |
| `/sim/ground_truth/robot_0/odom` | nav_msgs/msg/Odometry | world 真值，仅评测 | reliable、depth 10 |
| `/sim/ground_truth/robot_0/contacts` | litesim3d_interfaces/msg/Contact | 碰撞事件，仅评测 | reliable、depth 10 |

`namespace:=robot` 使相对话题变为 `/robot/cmd_vel`、`/robot/points_raw` 等；`/clock`、`/sim/status`、服务和真值通道仍是绝对名称。单机 `robot.id` 决定真值路径，不自动跟随 namespace。

### 10.2 服务表

| 服务 | 类型 | 可用入口 |
| --- | --- | --- |
| `/sim/pause` | std_srvs/srv/SetBool | 单机、多机、会话 |
| `/sim/step` | litesim3d_interfaces/srv/Step | 单机、多机、会话；暂停后使用 |
| `/sim/set_pose` | litesim3d_interfaces/srv/SetPose | 单机；仅实验开始前 ready |
| `/sim/reset` | litesim3d_interfaces/srv/Reset | 仅 `sim_session`，管理单机完整会话 |

接口可在本机查看：

```bash
ros2 interface show litesim3d_interfaces/srv/Step
ros2 interface show litesim3d_interfaces/srv/SetPose
ros2 interface show litesim3d_interfaces/srv/Reset
ros2 interface show litesim3d_interfaces/msg/Contact
```

Contact 含 `header`、`run_id`、`robot_link`、`entity`、`clearance`；其 world 坐标语义与普通算法局部 odom 分开。

### 10.3 时钟与 TwistStamped

每次新实验从 1 ns 仿真时间开始。所有数据时间戳来自同一仿真时间轴；所有需要时间的算法节点设置 `use_sim_time: true`。一个 domain 只能有一个 `/clock` 发布源；并行启动两份单机仿真会触发故障，应改用 world 或不同 domain。

Stamped 命令必须使用当前仿真时钟，而不是 `time.time()`、电脑日期或 ROS 默认墙钟。时间戳必须不晚于当前仿真时间，且不早于 `当前时间−command_timeout`。多机要求 frame 精确匹配，如 `r0/base_link`；单机也建议始终使用准确的带前缀 base_link。

本文 `ros_client.py --stamped` 已启用 use_sim_time，并等待时钟有效后发送；可以直接参考其写法。暂停时基于 ROS 时间的 timer 不会继续触发，必要的运行监测/超时应明确使用墙钟。

### 10.4 TF 发布责任

默认 R01 单机 TF：

```text
odom ──仿真桥接──> base_link ──robot_state_publisher──> lidar_link
                            ├──────────────────────> left_wheel
                            └──────────────────────> right_wheel
```

实际桥接发布的是 `odom → URDF root`。如果 URDF root 是 `base_footprint`，则链为 `odom → base_footprint → base_link → 传感器`；root 到 base 的固定偏移由 RSP 发布。里程计消息 child_frame_id 仍为配置的 base_link。

| TF 边 | 谁负责 |
| --- | --- |
| URDF 内部各 link | robot_state_publisher，消费 joint_states |
| odom → URDF root | 默认仿真桥接；外部估计器接管时关闭桥接这一条 |
| map → odom | 外部定位/SLAM；仿真不注入真值 map TF |
| world → 每个 odom | 当前没有提供通用发布；真值留在评测通道 |

外部估计器应尊重 URDF root/base 关系，不能在已有 `root → base_link` 的情况下再给 base_link 添加一个不同父节点。不要同时由多个节点发布同一 odom TF。多机还检查错误父 frame，发现冲突会使世界退出；单机也检查重复 odom TF 发布源。

检查 TF：

```bash
ros2 run tf2_ros tf2_echo odom base_link --ros-args -p use_sim_time:=true
ros2 run tf2_ros tf2_echo base_link lidar_link --ros-args -p use_sim_time:=true
```

检查完按 Ctrl+C 关闭；这些观察节点若跨越协调 reset 存活，需要登记为 observer 或成员。

### 10.5 QoS 如何匹配

默认点云/IMU 发布 best effort。若消费端要求 reliable，它无法与 best effort 发布者匹配。优先使用：

```python
from rclpy.qos import qos_profile_sensor_data
node.create_subscription(PointCloud2, 'points_raw', on_cloud, qos_profile_sensor_data)
```

或 C++ 的 `rclcpp::SensorDataQoS()`。必须使用 reliable 的消费者，可在单机高级入口设置节点参数 `sensor_reliable:=true`，或在 world launch 设置同名参数。reliable 发布者也能匹配 best effort 订阅者；这不意味着每个接收器一定不丢帧。

```bash
ros2 topic info /points_raw --verbose
ros2 topic echo /points_raw --field header --once --qos-reliability best_effort
```

发布端 `qos_conflicts`、`dropped_frames`、`internal_missed_scans` 与 DDS 接收端实际丢帧不是同一个指标。发布端无法完整知道 DDS 交付丢失，需消费端按扫描时间戳检查缺口。

## 11. 接入自己的算法或控制器

### 11.1 最小接入顺序

1. 先运行本文示例并确认 clock、points、odom、IMU 正常。
2. 给算法设置 `use_sim_time: true`；核对雷达/IMU消息类型、字段名、时间单位和 QoS。
3. 将算法输入 remap 到对应话题，单机如 `/points_raw`、`/imu/data_raw`、`/odom`；多机加 `/r0/` 等前缀。
4. 配置 TF frame：odom/base/lidar/IMU 必须与消息一致，安装外参从 URDF 固定变换核对。
5. 确定 map→odom 与 odom→root 的唯一发布者。估计器接管 odom TF 时关闭仿真桥接发布。
6. 将控制输出接到对应 `/cmd_vel`；类型匹配 Twist 或 TwistStamped，只使用 vx/ωz，并持续刷新。
7. 分别验证传感器消费、估计输出和反馈控制，再开展任务级建图/定位/导航验收。

不同算法的参数名不同。以下是**需要按算法替换占位项的 ROS 命令模板**，不是随附可执行算法：

```text
ros2 run <算法包> <算法可执行文件> --ros-args \
  -p use_sim_time:=true \
  -r <点云输入话题>:=/points_raw \
  -r <IMU输入话题>:=/imu/data_raw \
  -r <里程计输入话题>:=/odom
```

有的算法直接消费 `time` 秒，有的要求 `t` 纳秒或其他字段；有的要求经过排序或去畸变的点云。按目标算法实际约定做适配，不能只改 topic 名便认定兼容。若算法需要二维 LaserScan、地图服务器、代价地图或导航 action，本项目没有自动提供这些完整链路，需要在算法侧配置/转换。

### 11.2 随附 Python 接入程序

文件：[ros_client.py](../examples/ros_client.py)。它展示 ROS 时间、sensor QoS、odom 订阅和两种速度发布方式；退出时发送零速度，输出通信和位姿统计。

| 命令 | 行为 |
| --- | --- |
| `python3 docs/examples/ros_client.py --duration 5` | 单机只读订阅 |
| `… --drive --linear 0.2 --angular 0.1` | 显式发送 Twist，默认运行 5 秒墙钟 |
| `… --drive --stamped` | Stamped 控制；仿真端必须已选择 stamped |
| `… --namespace r0 --drive --stamped` | 控制 r0，frame 默认 r0/base_link |
| `… --frame robot/base_footprint` | 覆盖命令 frame；仅在与配置 base_link 一致时使用 |
| `… --output evidence/manual/client.json` | 保存 JSON 统计 |

该脚本固定订阅相对 `points_raw`、`imu/data_raw`、`odom`；自定义话题时修改示例或在自己的节点中 remap。IMU 是可选输入，脚本的 connected 判据只要求 clock、points、odom。它不做避障、定位或轨迹跟踪，不能作为导航成功判据。

### 11.3 建图/定位/导航需要额外检查什么

| 阶段 | 最小检查 | 常见遗漏 |
| --- | --- | --- |
| 三维建图输入 | xyz 有限性、ring、逐点 time、外参、时间同步 | 把 rolling 云当作去畸变云；秒/纳秒混淆 |
| 定位/里程计 | 连续估计、正确 frame、TF 唯一发布者 | 把理想 odom 作为算法效果；TF 双重发布 |
| 导航控制 | 估计反馈→规划/控制→cmd_vel→运动→传感器反馈 | 只发送速度，没有经过定位/规划闭环 |
| 评测 | 真值独立记录、初始对齐、超时和失败统计 | 将 ground truth 接入算法而没有披露 |

评估外部估计器时可启用 noisy odom；是否消费 odom 由算法设计决定。不要将 `/sim/ground_truth/*` 作为定位或控制输入后声称验证了传感器估计能力。当前文档没有冻结一个必须安装的 SLAM/Nav2 组合。

## 12. 多机器人仿真

### 12.1 启动两台机器人

先停止其他仿真。终端 A：

```bash
evidence_dir="$(python3 scripts/paths.py evidence)"
mkdir -p "$evidence_dir"
ros2 launch litesim3d_ros2 world.launch.py \
  config:="$PWD/docs/examples/world.yaml" \
  manifest:="${evidence_dir}/manual-world.json"
```

world 文件内容：

```yaml
schema_version: 1
config: robot.yaml
robots:
  - {id: r0, xyz: [0, 0, 0], rpy: [0, 0, 0]}
  - {id: r1, xyz: [0, 2, 0], rpy: [0, 0, 0]}
```

`config` 指向普通单机配置。world 中每个 xyz/rpy **覆盖**公共配置的 initial_pose，不是叠加偏移；rpy 缺省零。每台机器人有自己的 odom 原点，因此 r1 虽在 world 的 y=2，其初始 `/r1/odom` pose 仍接近零。

终端 B：

```bash
python3 docs/examples/ros_client.py --namespace r0 --drive --duration 5
python3 docs/examples/ros_client.py --namespace r1 --duration 5
```

只给 r0 发命令时，r1 保持静止；r0 点云仍能看到 r1。`/sim/pause` 和 `/sim/step` 操作整个世界。

### 12.2 名称、限制和参数责任

| 内容 | r0 示例 |
| --- | --- |
| 速度、传感器 | `/r0/cmd_vel`、`/r0/points_raw`、`/r0/imu/data_raw` |
| 里程计、关节、描述 | `/r0/odom`、`/r0/joint_states`、`/r0/robot_description` |
| TF frame | `r0/odom`、`r0/base_link`、`r0/lidar_link` |
| 真值 | `/sim/ground_truth/r0/odom`、`/sim/ground_truth/r0/contacts` |
| 共享接口 | `/clock`、`/tf`、`/tf_static`、`/sim/status`、pause/step |

机器人数量为 1–4，ID 正则为 `[A-Za-z][A-Za-z0-9_]*` 且唯一。所有机器人共用 URDF、传感器、驱动和场景；传感器 topic 不可带前导 `/`。模型 collision 几何总数最多 256。初始机器人之间及与障碍不能碰撞。

世界统一步进，所有机器人状态推进完成后再生成扫描；射线线程预算最多 4，不能理解为每台机器人各有 4 个并行射线线程。随机流按机器人隔离。

### 12.3 Stamped、可靠传感器与 TF 接管

```bash
ros2 launch litesim3d_ros2 world.launch.py \
  config:="$PWD/docs/examples/world.yaml" \
  cmd_mode:=stamped sensor_reliable:=true
```

配套控制：

```bash
python3 docs/examples/ros_client.py --namespace r0 --stamped --drive --duration 5
```

如果外部估计器只接管 r1 的 odom TF，启动时再加 `external_odom_tf_robots:=r1`。这时必须启动外部 TF 发布者才能得到完整 r1 的 TF 树。全部接管则用 `publish_odom_tf:=false`。引用不存在或重复的 ID 会拒绝。

多机没有 `/sim/set_pose`、完整 reset 管理器、单机 `/scene` 和 `/trajectory` 可视化输出。重新设置初值时停止完整 world launch 后重启。不要用多份独立 sim_node 在同一 domain 拼接多机世界。

## 13. Ouster 字段适配与 PCL 消费

这是从通用 xyzirt_v1 到冻结的 Ouster `original` 格式的字段适配。保留原 frame、header、点坐标和组织尺寸，不模拟某型号 Ouster 的真实回波物理。

已有单机仿真时，分别在两个已完成 2.2 的终端运行：

```bash
ros2 run litesim3d_ros2 sim_ouster_adapter --ros-args \
  -p input_topic:=/points_raw -p output_topic:=/points_ouster
```

```bash
ros2 run litesim3d_ros2 sim_cloud_probe
```

第三个终端检查：

```bash
ros2 topic echo /adapter_status --once
ros2 topic echo /probe_status --once
```

多机将 input_topic 改为 `/r0/points_raw`。多个适配器/探针可分别放进 namespace，例如适配器用 `-r __ns:=/r0 -p input_topic:=points_raw -p output_topic:=points_ouster`，探针用 `-r __ns:=/r0`，其状态话题也会加前缀。

适配器 input_topic 默认 points_raw，output_topic 默认 points_ouster；输入、输出默认使用 SensorDataQoS（best effort、KEEP_LAST 5）。适配器支持 `-p sensor_reliable:=true`，同时把输入和输出设为 reliable；此时上游仿真器也必须开启 reliable，队列深度仍为 5。

`adapter_status` 每 200 ms 及每次处理点云后发布 `accepted`、`rejected`、`error`，以及实际 DDS 匹配数 `input_publishers`、`output_subscribers`。由会话管理器启动时还带当前 `run_id`，独立启动时该值为空。暂停单步前可据此确认新实验段中的上下游已匹配，且尚未消耗第一帧。

| 输出字段 | 偏移 | 类型 | 语义 |
| --- | --- | --- | --- |
| x/y/z | 0/4/8 | float32 | 米 |
| intensity | 16 | float32 | 原归一化合成强度 |
| t | 20 | uint32 | 相对 header 的纳秒，由原 time 秒值四舍五入 |
| reflectivity | 24 | uint16 | 有效点 intensity×65535 四舍五入，非真实标定反射率 |
| ring | 26 | uint16 | 原线号 |
| ambient | 28 | uint16 | 0，未建模 |
| range | 32 | uint32 | 距离毫米，无效点 0 |

小端、48 字节 point_step，偏移 12 是 PCL 齐次坐标 1，其余填充为 0。无回波 xyz 保留 NaN。布局、长度、时间或范围越界时拒绝整帧，并在 adapter_status 记录 rejected/error。

`sim_cloud_probe` 实际读取所有这些字段，过滤非有限坐标，再执行 0.1 m PCL VoxelGrid；状态报告有限点数、体素数、质心等。它是字段消费验证，不是建图或导航程序。字段定义与冻结依据见 [M3 基线](../testing/M3基线.md)。

## 14. 单机会话重置

### 14.1 什么时候用 `sim_session`

反复从同一初始条件做实验，并需要算法、控制器、TF 缓存随仿真一起重建时，使用会话管理器。它**代替** demo launch，自己启动单机 sim_node 和 RSP，并管理已登记成员。当前入口面向根命名空间单机；没有自动多机完整重置。

先停止当前 launch、控制脚本和其他实验进程，然后在终端 A：

```bash
evidence_dir="$(python3 scripts/paths.py evidence)"
mkdir -p "$evidence_dir"
lws_session_dir="$(mktemp -d "${evidence_dir}/manual-session-XXXXXX")"
ros2 run litesim3d_ros2 sim_session \
  --config "$PWD/docs/examples/robot.yaml" \
  --output "$lws_session_dir"
```

每次启动使用新输出目录，避免和已有 `epoch-0001` 冲突。启动和每次 reset 后都保持 paused。

终端 B：

```bash
ros2 topic echo /sim/status --once
ros2 service call /sim/pause std_srvs/srv/SetBool '{data: false}'
```

这个入口默认 Twist、best effort 传感器、仿真发布 odom TF。可加 `--sensor-reliable` 让子仿真节点以 reliable 发布点云和 IMU。其他高级 sim_node 参数未暴露，不接受直接追加 `--ros-args -p cmd_mode:=…` 来改其子节点。

### 14.2 注册算法/消费端

管理器可登记最多 32 个成员，每项必须包含 `name` 和 `argv`，可选 `ready_topics`：

```json
[
  {
    "name": "实际ROS节点名",
    "argv": ["绝对可执行文件路径", "参数1", "参数2"],
    "ready_topics": ["/points_raw", "/odom"]
  }
]
```

`name` 必须与进程实际出现在 ROS 图中的节点名一致，且不重复。argv 直接执行，不经过 shell，不会展开 `$HOME`、`~` 或 shell 重定向；推荐使用绝对路径。正式算法多进程/多节点部署时，应确保所有相关节点均纳入重置责任。

成员须开启标准参数服务，并在建立输入订阅后启动 executor。会话管理器等待空 `get_parameters` 请求获得响应、ROS 图补齐节点/端点归属及新仿真器状态更新，核对订阅类型/QoS 和发布端 DDS 匹配数后才认为成员就绪。`ready_topics` 列出必须建立的输入，支持当前配置中的雷达/IMU 话题及 `/clock`、`/odom`、`/joint_states`；异步初始化的节点应显式填写。省略时自动收集已发现的输入，重置时还会保留旧 epoch 的输入要求。它不检查算法内部地图或模型是否加载完成，应用须自行管理更高层的就绪状态。

`/sim/status` 的 `ready` 只表示仿真内核和 RSP 就绪。带成员的首次启动，应等待 `session.jsonl` 中当前 epoch 的 `ready`；重置则等待 `/sim/reset` 成功返回，再立即单步或恢复运行。失败时管理器不会返回成功，并在记录中标明缺失订阅、QoS 不兼容、executor 未响应或成员退出。

best effort 即使已匹配也允许丢包。要求暂停后的唯一首帧可靠送达时，使用 `sim_session --sensor-reliable`，所有相关消费端也请求 reliable；随附适配器使用 `--ros-args -p sensor_reliable:=true`。适配器输出属于下游链路，外部消费者须在单步前等待自己的 DDS 发布端匹配。可靠传输保持 KEEP_LAST 5，不替代慢消费者的缓存/吞吐验收。

下面生成一个**可直接运行**的成员文件，登记随附适配器：

```bash
evidence_dir="$(python3 scripts/paths.py evidence)"
mkdir -p "$evidence_dir"
export LITESIM3D_EVIDENCE_DIR="$evidence_dir"
python3 - <<'PY'
import json
import os
from pathlib import Path
from ament_index_python.packages import get_package_prefix
executable = Path(get_package_prefix('litesim3d_ros2')) / 'lib/litesim3d_ros2/sim_ouster_adapter'
members = [{'name': 'sim_ouster_adapter', 'argv': [str(executable)], 'ready_topics': ['/points_raw']}]
(Path(os.environ['LITESIM3D_EVIDENCE_DIR']) / 'manual-members.json').write_text(json.dumps(members, indent=2))
PY
lws_session_dir="$(mktemp -d "${evidence_dir}/manual-session-XXXXXX")"
ros2 run litesim3d_ros2 sim_session \
  --config "$PWD/docs/examples/robot.yaml" \
  --output "$lws_session_dir" \
  --members "${evidence_dir}/manual-members.json" \
  --timeout 15
```

先关闭上一份 sim_session 再运行此命令。`--timeout` 是启动/重建等待上限，单位墙钟秒，默认 15，范围 [1,120]。成员进程环境还包含 `LWS_RUN_ID` 和 `LWS_RUN_DIR`，可用于把算法日志写入对应实验段。

### 14.3 发起 reset

先停止手动控制器，以及临时 `ros2 topic echo`、`tf2_echo`、bag 等未登记的持续消费进程。用一次性状态查看获得当前 `run_id`：

```bash
ros2 topic echo /sim/status --once
```

找到 values 中 key 为 `run_id` 的 value，替换以下变量内容后执行：

```bash
lws_run_id="替换为刚读取的run_id"
ros2 service call /sim/reset litesim3d_interfaces/srv/Reset \
  "{request_id: 'reset-001', expected_run_id: '$lws_run_id', set_initial_pose: false}"
```

返回 `success: true` 和**新的** run_id 后，再调用 pause=false 继续。若要换初始位置，使用新 request_id，并给出完整单位四元数：

```bash
ros2 service call /sim/reset litesim3d_interfaces/srv/Reset \
  "{request_id: 'reset-002', expected_run_id: '$lws_run_id', set_initial_pose: true, initial_pose: {position: {x: -1.0, y: 0.0, z: 0.0}, orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}}}"
```

第二个例子前要重新读取当前 run_id 并更新变量。不能使用墙钟旧记录里的 run_id；不能把四元数 w 留为默认 0。新位姿先预检，非法姿态、穿透或缺少支撑等导致预检失败时保留旧实验。

同一 request_id 与相同载荷重发返回缓存结果；同 ID 改载荷拒绝。ID 非空且最多 128 字节，缓存最多 4096 项。新一次重置用新 ID。

### 14.4 重置范围与输出

重置顺序是：校验请求和参与者→预检新初值→停止成员→停止仿真/RSP→创建新 run_id→重启 RSP/仿真→重启成员→保持 paused。只管理自己启动的进程；必需成员异常退出会使会话失败，而不会只因主管进程还活着就报告健康。

未登记的 clock/TF/odom/传感器订阅者会阻止 reset。确实只观察、不保留算法历史的节点可重复传入 `--observer 节点名`；名称以 `ros2 node list` 为准。observer **不能豁免未管理的 cmd_vel 发布者**。需要严格清空历史的 RViz、估计器和控制器应登记为成员；跨 reset 保留的只读观察端需自行处理时间回退和缓存。

输出目录含 `session.jsonl`，记录 run_id、进程 PID、启动/退出/重置；每个 `epoch-*` 有独立日志和 manifest。数据记录以 epoch 分段，避免将时钟回到 1 ns 前后的数据误当作同一条连续时间轴。

## 16. 记录数据、运行清单和离线评测

### 16.1 运行清单不是完整数据录制

启动时提供 `manifest`（launch）或 `manifest_path`（节点）。记录目录先创建，文件名每次实验尽量不同；同一路径会在本次运行状态更新时覆写快照。

运行清单用于追溯以下内容：

- run_id、状态、仿真时间、退出原因。
- 核心/桥接源码指纹、配置和模型资源 SHA-256、URDF 导入报告。
- 解析后参数、命令生效步号、接触事件、动态物体冻结时刻。
- ROS/RMW 环境及接口配置；多机包含每台机器人的状态与 TF 发布责任。

命令/接触内存记录有 `journal_limit` 上限，总量和截断量另记。manifest 不包含完整传感器序列，不能替代 bag，也不能将其中有限的最近输入当成完整回放记录。

### 16.2 用 rosbag2 录制

已有单机仿真时，在新终端执行：

```bash
evidence_dir="$(python3 scripts/paths.py evidence)"
mkdir -p "$evidence_dir"
ros2 bag record --use-sim-time \
  -o "${evidence_dir}/manual-bag-$(date +%Y%m%d-%H%M%S)" \
  /clock /tf /tf_static /cmd_vel /points_raw /imu/data_raw /odom \
  /joint_states /sim/status /sim/ground_truth/robot_0/odom \
  /sim/ground_truth/robot_0/contacts
```

按 Ctrl+C 正常关闭 recorder，让元数据落盘。多机把各机器人话题展开列出；真值和传感器可以同包保存，但算法订阅仍需隔离。使用 session reset 前停止 recorder，并为新 epoch 开新 bag，或把 recorder 纳入明确的会话管理。

录完检查：

```text
ros2 bag info <刚生成的bag目录>
```

核对各话题消息数、类型、时长和实际点云时间戳缺口。若消费端需要特定 QoS，Humble 的 recorder 支持 `--qos-profile-overrides-path`，依据 `ros2 topic info --verbose` 的实际发布 QoS 设置。

### 16.3 离线回放

先关闭实时仿真和原 RSP，另起只消费数据的算法节点并启用 use_sim_time。以下命令中的目录需要替换：

```text
ros2 bag play <bag目录> --clock \
  --topics /points_raw /imu/data_raw /odom /tf /tf_static
```

这里让 rosbag 生成唯一 `/clock`，明确不回放录制的 `/clock` 和 `/cmd_vel`。不要同时运行实时仿真，也不要额外启动一份发布同一 TF 的 RSP。多机回放时用对应前缀话题。

这是离线数据消费回放，不是重新执行物理仿真的确定性输入回放；若需要验证控制重演，必须额外设计命令生效步号和初始条件的对齐流程。

### 16.4 离线轨迹评测工具

`scripts/benchmarks/evaluate_m2.py` 接收 JSON **运行列表**；每条轨迹由 `{stamp_ns, xyz}` 样本组成。简化的输入结构为：

```json
[
  {
    "completed": true,
    "timed_out": false,
    "alignment": [0.0, 0.0, 0.0],
    "truth": [{"stamp_ns": 100000001, "xyz": [1.0, 0.0, 0.0]}],
    "estimate": [{"stamp_ns": 100000001, "xyz": [0.98, 0.0, 0.0]}]
  }
]
```

保存成真实文件后运行：

```text
python3 scripts/benchmarks/evaluate_m2.py <输入运行列表.json> <输出评分.json>
```

当前工具按每个真值样本匹配最近未用估计样本，默认时间容差 5 ms，匹配率≥99%、位置 RMSE≤0.1 m、completed=true、timed_out=false 且无非法估计才通过；所有运行通过才返回 0。

alignment 是预先确定的固定 **xyz 平移**，不是拟合整条轨迹，也不做旋转/尺度拟合。非零初始航向时，先在数据导出阶段按已冻结规则统一坐标方向，再使用此工具。它不直接读取 ROS bag、不评测完整姿态/导航成功率，也不自动生成 SLAM 输出。

## 17. 性能调整与运行检查

### 17.1 调参顺序

| 现象/目标 | 优先调整 | 代价与边界 |
| --- | --- | --- |
| 初次接入只看接口 | 16×512、10 Hz、1–2 个线程，少量实体 | 先保证模型/时间/TF 正确 |
| 点云计算慢 | 降 columns/rings/rate_hz；线程从 1 调到 2 或 4 | 分辨率/频率降低；线程最多 4 |
| 碰撞开销高 | 简化 collision，保留需要的 sensor_geometry | 碰撞形状改变会影响可通行性 |
| 加快离线实验 | ROS 的 real_time_factor=0 | 实际速度由 CPU/场景决定，不保证固定倍速 |
| 更细运动积分 | 减小 step_size | 开销与历史预算增加，传感器频率不会自动改变 |
| rolling history 不足 | 增大 history_limit 或降低事件率 | 最多 65536，仍须通过预检 |
| 接收端跟不上 | 减少重计算/打印、检查 QoS 和消费队列 | reliable 不能代替消费端性能设计 |
| 算法使用带噪数据 | 固定 seed，显式设定各 sigma/bias | 保留零噪基线，以区分算法误差和传感器误差 |

过载时内核会减慢仿真，而不是跳过内部扫描来维持表面帧率。真实倍速用 `仿真时间增量 / 墙钟时间增量` 计算；`ros2 topic hz` 是接收端观测，不能单独证明调度和交付都无丢帧。

### 17.2 诊断字段

```bash
ros2 topic echo /sim/status --once
```

| 字段 | 解释 |
| --- | --- |
| ready / state / run_id | 依赖是否就绪、ready/running/paused/fault 等状态、实验标识 |
| subscription_matches | 单机发布端按话题记录的 DDS 订阅匹配数；用于会话启动/重置就绪检查，不是消息送达计数 |
| step / time_ns | 当前物理步数和仿真时间 |
| rejected_commands / last_error | 被拒绝控制数及最近错误 |
| command_timeout | 当前是否触发控制看门狗；无控制的静止实验也可能显示此项 |
| contact_count | 接触事件数量；结合具体实体和位姿排查 |
| published_clouds / published_imus | 桥接实际发布计数；多机按状态项查看相应计数 |
| qos_conflicts | 不兼容 QoS 事件计数 |
| sensor_queue_policy / sensor_queue_depth | 实际传感器可靠性及 depth 5 |
| compute_p99_ms / bridge_p99_ms | 有界窗口中的射线计算和桥接延迟 p99 |
| internal_missed_scans / dropped_frames | 内部漏扫描、显式丢弃计数；不代表接收端 DDS 丢失已知 |
| retained_inputs / evicted_inputs | 保留与截断的命令日志数量 |
| trajectory_samples / scene_bvh_builds | 轨迹历史量和场景索引重建计数 |

不同入口的诊断项有差异，以实际 values 为准。存在警告时看具体字段，不要仅凭等级推断程序崩溃。

### 17.3 用户接入后的必要检查

1. 模型能通过独立加载，单位、轮径、轮距和初始碰撞正确。
2. clock 唯一；消息 frame、QoS、采样时间和预期一致。
3. 有效速度能运动，零命令/超时能停车；非法命令可在状态中解释。
4. 暂停/单步行为正确；rolling 数据按逐点时间使用。
5. 算法输出和 TF 无重复发布；多机命令不会串到另一机器人。
6. 记录配置、manifest、bag 和算法结果，按任务门槛判断是否通过。

### 17.4 修改代码后的回归

完整回归、性能测量、安装验证和测试结果见 [测试入口](../testing/README.md)。接入检查只确认当前场景的操作和接口，不能代替平台或长期稳定性验收。

## 18. 常见问题

| 现象/提示 | 原因方向 | 处理 |
| --- | --- | --- |
| `ros2: command not found` | 未进入 Humble | 激活 Humble 环境，Ubuntu Bash 使用 `source /opt/ros/humble/setup.bash` |
| package/executable not found | 没有 source 本项目安装，或临时安装已清理 | 运行 python3 scripts/paths.py install；必要时重新构建 |
| 构建找不到 PCL/FCL/urdfdom | 环境依赖或 CMake 搜索路径不完整 | 在正确 Humble 环境构建，按包依赖定位；不要随意修改全局编译器 |
| 中文路径下 rosidl 失败 | 消息生成工具路径兼容性 | 使用 scripts/build.sh 的 ASCII 构建目录 |
| launch 报日志 PermissionError | 当前执行环境不能写默认日志目录 | 按 2.2 将 ROS_LOG_DIR 设为项目 evidence 子目录 |
| `unknown field` | 字段拼写或层级错误 | 对照本文配置表；区分 YAML/launch/节点参数 |
| 修改 YAML 后没变化 | 节点只在启动时读取，或读的是另一份文件 | 检查启动 config 路径和 manifest；完整重启 |
| 资源不存在/package URI 不可解析 | 相对基准改变或 description 包未 source | 按第 5 节核对 URDF/mesh 路径 |
| `missing collision` | 有 visual、无 collision | 补 collision，或明确开启 visual_collision_fallback |
| `wheel_radius/separation differs from URDF` | YAML 与模型不一致 | 按米核对半径、轮原点和左右顺序，不放宽单位错误 |
| `wheel axis must point along base +y` | 关节轴在 base 中方向不符 | 检查 joint origin 的旋转及 axis 的组合 |
| 起始碰撞/缺少支撑 | base 定义错误、障碍重叠、地形层不匹配 | 检查 initial_pose、轮高、clearance、support 和三角面法向 |
| `robot_state_publisher readiness timeout` | RSP 未启动、namespace/name 不一致或未订阅正确 joint_states | 优先用 launch；高级入口核对两个进程参数 |
| 看到点云 topic 但没数据 | paused、QoS 不兼容、rolling 尚未采完整帧 | 查 status，使用 best effort 订阅，继续/单步足够时间 |
| `qos_conflicts` 增加 | 消费端要求 reliable，发布端 best effort | 修改消费者 QoS 或重新以 sensor_reliable=true 启动 |
| robot 不运动 | 命令话题/类型/frame 错误，或碰撞/限坡/暂停 | 查 rejected_commands、last_error、state、contacts |
| Stamped 被拒绝 | 使用墙钟、旧时钟、未来时间或跨机器人 frame | use_sim_time=true；读取当前时钟；正确带前缀 base frame |
| Ackermann v=0、ω≠0 不转 | 模型不允许原地转向 | 给出可行线速度/曲率，或选择差速底盘 |
| IMU 静止时 z≈9.80665 | raw 加速度包含重力对应的比力 | 按算法原始 IMU 约定处理，不直接减掉后又让算法再减一次 |
| RViz Fixed Frame 报错 | frame 不存在、前缀不一致或 TF 被关闭 | 默认使用 odom；多机 r0/odom；检查 TF 唯一发布者 |
| `multiple /clock publishers` | 同 domain 启动多份仿真/回放 | 关闭重复来源；多机用 world，独立实验用不同 domain |
| 重复 odom TF/错误父节点 | 仿真和估计器同时发布，或前缀/root 配置错 | 关闭被接管的仿真 TF，核对 URDF root/base 链 |
| `/sim/set_pose` 在暂停时拒绝 | paused 已不是启动前 ready | 修改初值重启，或使用 sim_session reset |
| `/sim/reset` 不存在 | 用的是普通 launch 而非 session | 用 sim_session 启动单机实验 |
| reset 报 uncoordinated participants | 仍有未登记订阅者或控制发布者 | 停止临时工具；把算法登记为 member，纯观察者按需登记 |
| reset 报 stale expected_run_id | 用了上一实验 ID | 重新读取 status；新操作用新 request_id |
| 单步预算不足/缓存满 | 单次输出太大或请求数达到上限 | 减少每批 steps；缓存满后新建实验 |
| 雷达看见自身车体 | 默认仅排除 sensor_link | 按用途改为 self_filter=robot 或指定 excluded_links |
| world 中 r1 初始 odom 为零 | 每个机器人独立局部原点 | 全局初值从 world 配置/真值评测获取，区分坐标系 |
| 实测 Hz 低于配置 | RTF<1、暂停、接收端拥塞或丢包 | 同时检查仿真时间、墙钟、状态和接收时间戳缺口 |
| 停止单个子进程后整个 launch 结束 | 必需进程失败传播 | 正常结束按完整 launch 的 Ctrl+C；排查最先退出进程的日志 |

RSP 可能提示根 link 含 inertia、KDL 不支持根惯性。该仿真使用运动学，这条提示本身不表示模型/TF 启动失败；需要兼容其他动力学软件时按其要求增加固定 dummy root，并同步检查本项目 root/base TF 关系。
