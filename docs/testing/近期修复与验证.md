# 近期修复与验证

记录日期：2026-10-18。除单独标明的 Linux CI 排查外，以下为本机 macOS arm64 / RoboStack ROS 2 Humble 的实际执行结果。报告对应当时的源码与证据；原始文件位于外部 `evidence/`，路径解析见 [测试入口](README.md)。

## Linux CI 排查

[首轮实际执行的 Linux CI](https://github.com/chiway-luo/litesim3d_ros2/actions/runs/39116168009) 中，5 个包构建成功，核心 142 项、报告工具 37 项和单机 launch 2 项通过；ROS 集成有 22 项失败、四轮示例有 2 项失败，多机 launch 随节点退出而中断。原始失败保留于该运行的 `m1-m3-test-evidence` artifact。

- `external_odom_tf_robots` 的空默认值 `{}` 在 GCC 下选中了无默认值的参数声明重载，多机器人节点报“静态类型参数必须初始化”。改为显式 `std::vector<std::string>{}`，已有多机器人启动/参数/隔离测试覆盖默认路径。
- 暂停后唯一的 best effort 首帧可能未到达消费端；仿真发布计数不等于接收计数。四轮测试先等待消费端发现发布者、仿真器确认 DDS 匹配；会话增加 `--sensor-reliable`，适配器增加同名 ROS 参数及带 run_id 的匹配状态。要求精确首帧或完整计数的测试在发布/订阅两端使用 reliable，仍保留默认 best effort 与不兼容 QoS 测试，不补发、不额外推进仿真，也不放宽 1 ns 首帧断言。
- 原来的 3 秒故障注入启动预算可能在正常 DDS 发现阶段耗尽。缺失订阅测试使用产品默认 15 秒预算，服务调用等待覆盖该上限；不响应 executor 的测试在有限期限内拒绝启动，允许 RMW 在服务发现或响应阶段报告超时。

最终提交是否通过，以 [Linux Actions](https://github.com/chiway-luo/litesim3d_ros2/actions/workflows/m1.yml) 对应提交的完整结果为准；本机验证不能替代 Linux、隐藏源码后的安装验证或 RViz 检查。

[后续 Linux 复测](https://github.com/chiway-luo/litesim3d_ros2/actions/runs/39123816560) 中，百次重置、全部会话测试及多机器人启动通过，剩余 5 项失败均为大点云的单步接收。相关几何/扫描表校验改用双端 reliable，多机也报告 `subscription_matches` 并在测试中等待匹配；默认 best effort 仍由普通示例及 QoS 矩阵覆盖。CI 拆分构建和回归步骤，构建成功后独立执行安装隔离及 RViz 检查，即使其他测试失败也收集它们的结果；任何失败仍使整轮 CI 失败。

## 重置后首帧偶发超时

旧管理器把“节点已发现”当作消费端就绪。节点可能在创建订阅和处理 executor 前已可见；DDS 发现也可能早于 ROS 图补齐端点归属。此时立即单步发布的 volatile / best effort 首帧可能丢失，暂停后没有后续帧补发。

延后 1.5 秒创建订阅的复现中，旧 reset 比订阅创建提前 1476 ms 返回；仿真发布了首帧，但消费端收到 0 帧。修复后，管理器确认成员参数服务能响应、当前 run_id 的状态已更新、输入订阅类型/QoS 与 DDS 匹配已就绪，再返回成功。可用 `ready_topics` 显式声明异步创建的输入；重置期间保持暂停，不通过额外仿真步绕过问题。
